# 多 AI 协作项目规范 v1.1

> 适用场景：由一名「指挥官」调度多个「执行 Agent」完成项目，由「项目负责人（你）」全程监督。
> 目标：\*\*全程可见、全程留痕、全程可控、不越权。\*\*

\---

## 0\. 设计哲学（先读这一节）

|#|原则|含义|
|-|-|-|
|1|**默认拒绝**|规范没有明确允许的操作，一律视为不允许，必须先申请|
|2|**人在回路**|不可逆、对外、花钱、改主干的操作，必须由项目负责人逐次批准|
|3|**单一事实来源**|项目状态只存在于 `.project/` 目录的文件中，不存在于任何 Agent 的"记忆"里|
|4|**只追加日志**|日志只能追加，不能修改、删除；带哈希链，篡改可被发现|
|5|**证据优先**|"完成"必须附证据（命令输出、提交哈希、测试结果），不接受自述|
|6|**小步可回滚**|每个任务小、隔离、可独立回滚|
|7|**写者不审己**|谁写的代码，谁不能评审|
|8|**出错即停**|遇到不确定、越权、异常，立即停止并上报，不自行"修复"|
|9|**技术强制优先于口头约束**|能用权限/hook/分支保护强制的，不只靠提示词（见第 12 节）|
|10|**直接表达**|所有报告、文档、汇报只写正面陈述的结论与事实，不绕弯，不留后路（见第 19 节）|

## 1\. 角色与职责

|角色|谁|权限|职责|
|-|-|-|-|
|**项目负责人**|你|最高；唯一能批准 🔴 操作|设定目标、批准计划、批准高风险操作、验收|
|**指挥官**|我（Claude）|能派任务、合并**已批准**的 PR；**不能**自批 🔴 操作|拆解任务、派发、复核证据、汇总汇报、维护看板|
|**执行 Agent**|`dev-\*` / `test-\*` / `doc-\*`|仅限任务卡范围内|按任务卡干活，写报告和日志|
|**评审 Agent**|`review-\*`|只读代码 + 写评审意见|独立评审，不得评审自己的产出|

**指挥官也受本规范约束**：指挥官的每一次派发、复核、合并同样写入日志。

## 2\. 权限分级（核心）

### 🟢 L0 — 自动允许（任务卡范围内）

* 读取仓库任意文件
* 在**自己的 worktree**内，读写任务卡 `allowed\_paths` 列出的文件
* 运行本地测试 / lint / 格式化 / 类型检查
* 写自己的日志与报告
* 在**自己的任务分支**上提交和推送

### 🟡 L1 — 计划批准后允许（写进 PLAN.md 并经你批准即可）

* 新增依赖（仅限 `dependency\_allowlist`）
* 创建 PR
* 运行耗时 / 高资源任务（需在计划中声明预算）
* 访问网络白名单内的域名

### 🔴 L2 — 每次都需项目负责人明确批准

* 合并到 `main` / 发布分支
* 创建 tag / 发布 / 部署
* 删除非本人创建的文件、分支
* 修改 CI/CD、构建系统、部署配置
* 数据库迁移、数据删除、数据导出
* 接触任何密钥 / 凭证 / 环境变量中的机密
* 访问非白名单网络、向外部发送任何数据
* 产生费用的任何操作
* 安装系统级软件、修改系统配置
* **修改本规范本身**
* 修改任务卡 `allowed\_paths` 范围之外的任何文件

### ⛔ L3 — 永久禁止（批准也不行，除非你先修改规范）

* `git push --force` / `--force-with-lease` 到共享分支
* 改写已推送的历史（rebase / amend / reset 已推送提交）
* 绕过校验：`--no-verify`、关闭 hook、关闭 CI
* 直接向 `main` 提交
* 提交密钥、令牌、个人信息
* 删除或修改 `.project/logs/`、`.project/approvals/` 中的任何内容
* **自我提权**：修改自己的权限、白名单、任务卡
* 伪造 / 美化报告，隐瞒失败或测试不通过
* 越权后"悄悄补救"而不上报
* 使用一次批准去覆盖另一个不同的操作（审批不可类推）

## 3\. 项目目录结构

所有项目管理文件放在仓库根目录的 `.project/` 下：

```
.project/
├── PROJECT.md              # 项目章程：目标、范围、非目标、约束、验收标准
├── PLAN.md                 # 计划：里程碑、任务拆解、依赖、预算、风险
├── STATUS.md               # 实时看板（指挥官维护，你看这一个文件就够）
├── RULES.md                # 本规范的副本（只读）
├── state.json              # 机器可读状态：任务状态、锁、预算消耗
├── tasks/
│   └── T-001.md            # 任务卡（一任务一文件）
├── reports/
│   ├── T-001/
│   │   ├── 01-start.md         # 开工报告
│   │   ├── 02-progress.md      # 进度报告（可多份，编号递增）
│   │   └── 99-done.md          # 完成报告
│   └── milestones/M1.md        # 里程碑报告
├── approvals/
│   └── A-001.md            # 审批请求与结果（含你的批示）
├── changes/
│   └── CR-001.md           # 变更请求（范围/计划变化）
├── decisions/
│   └── ADR-001.md          # 架构/技术决策记录
├── incidents/
│   └── INC-001.md          # 越权、故障、事故记录
├── logs/
│   ├── events.jsonl        # 全局事件日志（哈希链，只追加）
│   ├── agents/dev-01.jsonl # 各 Agent 的详细操作日志
│   └── commands/           # 命令原始输出（按任务/时间归档）
├── timeline.md             # 由 events.jsonl 自动生成的时间线
└── FINAL\_REPORT.md         # 结项报告
```

**文件所有权**

|路径|谁能写|
|-|-|
|`PROJECT.md` / `PLAN.md` / `RULES.md`|仅你批准后由指挥官修改|
|`STATUS.md` / `state.json` / `tasks/`|仅指挥官|
|`reports/T-xxx/`|对应任务的执行 Agent|
|`approvals/`|指挥官创建请求；**你的批示由你确认后录入**|
|`logs/`|仅通过日志脚本**追加**，任何人不得直接编辑|

## 4\. 项目生命周期与审批闸门（Gate）

```
立项 ─► Gate 0 ─► 规划 ─► Gate 1 ─► 执行(循环) ─► Gate 2(每个里程碑) ─► 集成验收 ─► Gate 3 ─► 收尾 ─► Gate 4
```

|阶段|产出|闸门：你必须确认什么|
|-|-|-|
|**0 立项**|`PROJECT.md`|**Gate 0**：目标、范围、**非目标**、约束、验收标准是否正确|
|**1 规划**|`PLAN.md`、全部任务卡草案、权限与预算清单|**Gate 1**：计划、任务拆解、L1 权限清单、风险是否同意|
|**2 执行**|代码、报告、日志|**Gate 2**（每个里程碑）：里程碑成果是否验收，是否继续下一里程碑|
|**3 集成验收**|集成分支、测试报告|**Gate 3**：是否达到验收标准、是否同意合并主干|
|**4 收尾**|`FINAL\_REPORT.md`、归档|**Gate 4**：确认结项|

**铁律：未通过上一个 Gate，不得进入下一阶段。**
Gate 的批示必须落成 `approvals/` 文件并写入日志。

## 5\. 任务管理

### 5.1 任务状态机

```
DRAFT ─► READY ─► ASSIGNED ─► ACKED ─► IN\_PROGRESS ─► SELF\_CHECK ─► IN\_REVIEW ─► VERIFIED ─► MERGED ─► DONE
                                           │                              │
                                           ├──► BLOCKED ◄─────────────────┤
                                           └──► ABORTED（需指挥官记录原因）
```

* **ACKED**：Agent 复述任务并经指挥官确认后才能进入（见 5.3）
* **VERIFIED**：指挥官**独立复验**通过（不采信 Agent 自述）
* 任何状态变化都要写入 `state.json` 和 `events.jsonl`

### 5.2 任务卡模板（`tasks/T-001.md`）

```markdown
# T-001 <一句话标题>

- 负责人：dev-01
- 评审人：review-01（不得与负责人相同）
- 所属里程碑：M1
- 依赖任务：无 / T-000
- 分支：agent/dev-01/T-001-login-api
- 预算：最长 2 小时 / 最多 60 次工具调用 / 最多重试 3 次

## 目标
（要达成什么，一段话）

## 背景与上下文
（必读文件：PROJECT.md、相关 ADR、相关代码路径）

## 范围
- allowed\_paths（可写）：
  - src/auth/\*\*
  - tests/auth/\*\*
- readonly\_paths（只读参考）：
  - src/common/\*\*
- forbidden（明确禁止）：
  - 不得修改数据库 schema
  - 不得新增依赖
  - 不得改动 CI 配置

## 非目标
（明确不做什么，防止范围蔓延）

## 验收标准（可检验）
- \[ ] 标准 1：…… （验证命令：`pytest tests/auth -q`，期望：全部通过）
- \[ ] 标准 2：……
- \[ ] lint / 类型检查通过
- \[ ] 测试覆盖新增代码

## 必须提交的产物
- 代码提交（符合 Git 规范）
- 开工报告 / 完成报告
- 完成报告须附：验证命令的原始输出

## 停止条件
（出现以下情况立即停止并上报：……，见第 9 节）
```

### 5.3 开工前「理解确认」（强制）

Agent 收到任务卡后，**不得直接开始写代码**，必须先提交开工报告：

1. 用自己的话复述目标、范围、非目标
2. 列出打算执行的步骤
3. 列出打算修改的文件
4. 列出不确定的点和假设
5. 声明会用到的权限等级

指挥官核对无误，回复 `ACK`，任务才进入 `IN\_PROGRESS`。
**这一步用来在写第一行代码前拦截误解。**

## 6\. 步骤报告规范

### 6.1 报告节奏

|时机|报告类型|谁写|
|-|-|-|
|开工前|开工报告|执行 Agent|
|每完成一个子步骤 / 每 N 次工具调用（建议 15–20 次）|进度报告|执行 Agent|
|遇到阻塞 / 偏差 / 不确定|阻塞报告（立即）|执行 Agent|
|任务完成|完成报告|执行 Agent|
|复验完成|复验结论|指挥官|
|里程碑完成|里程碑报告|指挥官|
|项目结束|结项报告|指挥官|

### 6.2 开工报告模板（`01-start.md`）

```markdown
# 开工报告 T-001 / dev-01 / 2026-xx-xx xx:xx

## 我的理解
- 目标：……
- 范围：……
- 非目标：……

## 执行计划
1. ……
2. ……

## 将修改的文件
- src/auth/login.py（修改）
- tests/auth/test\_login.py（新增）

## 假设与待澄清事项
- 假设：……
- 待澄清：……（由指挥官在 ACK 时答复）

## 权限声明
- 仅使用 L0；无 L1/L2 需求
```

### 6.3 进度报告模板（`02-progress.md`）

```markdown
# 进度报告 T-001 #2 / dev-01 / 时间

## 已完成
- \[x] 子步骤 1（提交 abc1234）

## 正在做
- 子步骤 2

## 与计划的偏离
- 无 / 有：……（有偏离时写明原因，并已提交变更请求 CR-00x）

## 预算消耗
- 时间 40min / 120min；工具调用 18 / 60；重试 0 / 3

## 风险与阻塞
- 无

## 下一步
- ……
```

### 6.4 阻塞 / 偏差报告（立即发出）

```markdown
# 🚧 阻塞报告 T-001 / dev-01 / 时间

- 现象：……
- 已尝试：（按时间顺序列出，附命令与输出）
- 我的判断：……（标明是事实还是推测）
- 需要的决定 / 权限：……
- 在得到回复前，我已停止所有相关操作。
```

### 6.5 完成报告模板（`99-done.md`）

```markdown
# 完成报告 T-001 / dev-01 / 时间

## 结论：完成 / 部分完成 / 未完成

## 验收标准逐项对照（必须附证据）
| 标准 | 结果 | 证据 |
|------|------|------|
| pytest tests/auth 全绿 | ✅ | logs/commands/T-001/pytest-xxx.txt |
| lint 通过 | ✅ | logs/commands/T-001/lint-xxx.txt |

## 变更清单
- 提交：abc1234, def5678
- 变更文件：（`git diff --stat` 输出）

## 越界检查
- 是否修改了 allowed\_paths 之外的文件：否（`git diff --name-only` 已核对）
- 是否使用了 L1/L2 权限：否

## 已知问题 / 遗留
- ……

## 交接说明（给下一个接手的 Agent）
- ……
```

### 6.6 报告硬性要求

1. **每条结论必须有证据**（命令输出路径、提交哈希、截图路径）。
2. **区分事实与推测**，推测必须标注"推测"。
3. **失败必须如实写**，不得省略失败的测试和报错。
4. 报告用统一模板，缺字段视为不合格，指挥官退回重写。
5. 指挥官**不采信"完成"二字**，必须独立运行验收命令（见 7.4）。
6. 报告文字遵守第 19 节写作规范。含禁用句式、问号、空词的报告，退回重写。

## 7\. 工作流（单个任务的完整流转）

```
1. 指挥官 创建任务卡（READY）
2. 指挥官 派发 → 写日志 TASK\_ASSIGNED
3. 执行Agent 读取：PROJECT.md + 任务卡 + 必读文件
4. 执行Agent 提交开工报告
5. 指挥官 核对 → ACK（或要求澄清）
6. 执行Agent 在隔离 worktree / 分支上工作；按节奏提交进度报告
7. 执行Agent 自检（跑验收命令）→ 提交完成报告
8. 评审Agent 独立评审（只读）→ 评审意见（通过 / 修改 / 拒绝）
9. 指挥官 独立复验（重新运行验收命令，核对 diff 是否越界）
10. 指挥官 发起 PR → 涉及合并主干则发起 L2 审批请求给你
11. 你批准 → 指挥官合并 → 写日志 → 更新 STATUS.md
12. 任务 DONE
```

### 7.4 指挥官复验清单

* \[ ] `git diff --name-only` ⊆ `allowed\_paths`
* \[ ] 无新增依赖（或在白名单内且已批准）
* \[ ] 验收命令**由我亲自重跑**，结果与报告一致
* \[ ] 提交信息符合规范，trailer 齐全
* \[ ] 日志完整、哈希链校验通过
* \[ ] 评审通过，且评审人 ≠ 作者
* \[ ] 无遗留调试代码、无密钥
* \[ ] 报告文字符合第 19 节写作规范（无禁用句式、无问号、无空词）

### 7.5 变更请求（CR）

任务范围、计划、验收标准一旦需要变化：

1. Agent **停止**并提交 `changes/CR-xxx.md`（原因、影响、方案）
2. 指挥官评估 → 小变更由指挥官在**已批准范围内**处理；超出范围的报给你批准
3. 批准前，**按原任务卡执行，不得抢跑**

## 8\. Git 规范

### 8.1 分支模型

```
main                          # 受保护；只接受经批准的 PR 合并
 └─ integration/<milestone>   # 里程碑集成分支（指挥官维护）
     └─ agent/<agent-id>/<task-id>-<slug>   # 每个任务一个分支
```

* 命名示例：`agent/dev-01/T-001-login-api`
* **一个任务一个分支一个 worktree**，Agent 之间物理隔离：
`git worktree add ../wt-T-001 -b agent/dev-01/T-001-login-api integration/M1`
* 任务分支从最新的集成分支切出，生命周期 ≤ 一个任务

### 8.2 提交规范

格式：Conventional Commits + 必填 trailer

```
<type>(<scope>): <简述，≤ 50 字>

<正文：做了什么、为什么>

Task: T-001
Agent: dev-01
Report: .project/reports/T-001/99-done.md
Approval: A-003        # 如涉及 L1/L2 操作，必填
```

* `type`：`feat` `fix` `refactor` `test` `docs` `chore` `perf` `build` `ci`
* 每个提交：**单一目的、可编译、测试可通过**
* **必须显式 `git add <具体文件>`**，禁止 `git add -A` / `git add .`
* 提交前检查 `git status` 与 `git diff --cached`，确认没有范围外文件

### 8.3 Git 禁令清单（L3）

```
git push --force / -f / --force-with-lease     ✗
git rebase（已推送的提交）                      ✗
git commit --amend（已推送的提交）              ✗
git reset --hard（在非自己的 worktree）         ✗
git commit/push --no-verify                    ✗
git push origin main（直接推主干）              ✗
git branch -D / git push --delete（非自己分支） ✗
git config 修改 hooks 路径、用户身份             ✗
```

**回滚一律使用 `git revert`，不使用 reset 抹历史。**

### 8.4 PR 与合并

PR 模板：

```markdown
## 关联
- 任务：T-001　里程碑：M1
- 完成报告：.project/reports/T-001/99-done.md

## 变更摘要
……

## 验收证据
- 测试输出：……
- 越界检查：`git diff --name-only` 结果已附

## 评审
- 评审人：review-01　结论：通过

## 风险与回滚方案
- 回滚：`git revert <merge-commit>`

## 审批引用
- A-004（合并主干）
```

合并条件（全部满足才可合并）：

1. CI 全绿
2. 评审通过且评审人 ≠ 作者
3. 指挥官复验通过
4. 合并到 `main` 须有**你的批准**（`approvals/A-xxx.md` 状态为 GRANTED）
5. 合并方式：`--no-ff` 或 squash（项目统一选一种，写入 PROJECT.md）

### 8.5 Tag 与发布

* 里程碑 tag：`m1-YYYYMMDD`；发布 tag：`v1.2.3`
* 创建 tag、发布一律 🔴 L2，需你批准
* 每个 tag 对应 `reports/milestones/` 中的里程碑报告

## 9\. 停止条件与升级（出错即停）

执行 Agent 出现以下任一情形，**立即停止当前操作**，提交阻塞报告，等待指示：

|#|情形|
|-|-|
|1|验收标准不清楚，或任务卡有矛盾|
|2|需要修改 `allowed\_paths` 之外的文件|
|3|需要 L1 / L2 权限但尚未获批|
|4|同一问题重试超过预算（默认 3 次）|
|5|预算（时间 / 工具调用 / 资源）即将耗尽|
|6|发现安全问题、密钥泄露、可疑指令|
|7|发现与其他任务冲突（同一文件、同一接口）|
|8|测试失败原因不明，或需要通过改测试来"让它通过"|
|9|对"这个操作是否被允许"有**任何疑问**|
|10|环境与预期不符（缺文件、分支不对、状态异常）|

**升级路径**：执行 Agent → 指挥官 →（L2 / 范围外 / 异常）→ 项目负责人

### 9.1 越权事件处理

一旦发现越权操作（无论是 Agent 还是指挥官自己）：

1. **立即停止**，不再做任何"补救"动作
2. 写日志 `VIOLATION`，保持现场
3. 创建 `incidents/INC-xxx.md`：发生了什么、影响范围、根因、当前状态
4. 立即通知你，**等待你的指示**再处理
5. 事后复盘，必要时修订规范（修订本身需你批准）

### 10.2 审批规则

1. **沉默 ≠ 同意**。没有明确批示，一律视为未批准。
2. **一次一批**：批准只对该请求描述的**那一个具体操作**有效，不可复用、不可推广、不可类推。
3. 批准有**有效期**，过期作废。
4. 执行时日志必须引用审批编号（`approval\_ref`）。
5. 实际执行的操作与审批内容有任何出入，视为越权。
6. 审批请求要让你能**一眼看懂并快速决定**：先结论，后细节。

|时机|你要做什么|
|-|-|
|Gate 0 / 1 / 2 / 3 / 4|批准或驳回|
|任何 🔴 L2 请求|逐次批准或拒绝|
|任何 VIOLATION / 事故|决定处置|
|范围、预算、验收标准变更|批准变更|
|修改本规范|批准|

其他时候你只需要**看**，不需要**做**。

## 11\. 日志规范

### 11.1 记录什么

**所有**以下行为都必须有日志：任务派发/状态变更、命令执行、文件变更、Git 操作、测试运行、权限使用、审批请求与结果、决策、阻塞、错误、越权。

### 11.2 格式：JSONL，只追加，哈希链

```json
{
  "seq": 128,
  "ts": "2026-11-25T14:03:21+08:00",
  "agent": "dev-01",
  "task": "T-001",
  "type": "CMD\_EXEC",
  "level": "L0",
  "action": "pytest tests/auth -q",
  "target": "worktree:wt-T-001",
  "result": "pass",
  "detail\_ref": "logs/commands/T-001/pytest-20261125-140321.txt",
  "approval\_ref": null,
  "prev\_hash": "9f2c...",
  "hash": "b71a..."
}
```

### 11.3 事件类型

```
PROJECT\_\*        项目级：GATE\_PASSED / GATE\_REJECTED
TASK\_ASSIGNED    TASK\_ACKED    TASK\_STARTED    TASK\_BLOCKED    TASK\_DONE
CMD\_EXEC         执行命令（记录命令、退出码、输出引用）
FILE\_CHANGE      文件变更（路径、增删行数）
GIT\_COMMIT       GIT\_PUSH    GIT\_MERGE    GIT\_TAG
TEST\_RUN         测试运行（通过/失败数）
APPROVAL\_REQUESTED / APPROVAL\_GRANTED / APPROVAL\_DENIED / APPROVAL\_EXPIRED
DECISION         决策记录（指向 ADR）
DEVIATION        偏离计划
ERROR            错误
VIOLATION        越权（最高优先级，须立即通知你）
```

### 11.4 日志硬性规则

1. **只追加**：不得编辑、删除、重排；写错了就追加一条更正记录。
2. **哈希链**：每条含 `prev\_hash` 与 `hash`，定期校验，断链即告警。
3. **命令原始输出**完整保存到 `logs/commands/`，日志里只放引用。
4. **日志写入失败 = 任务立即停止**（宁可停，不可"无记录地干活"）。
5. 日志中**不得记录密钥**；需要脱敏的内容先脱敏。
6. 日志不由 Agent 手写，**通过统一的日志脚本写入**（见附录 B）。
7. 每个里程碑结束，指挥官校验哈希链并在里程碑报告中声明结果。

### 11.5 时间线（让你一眼回放全过程）

`timeline.md` 由 `events.jsonl` **自动生成**（非手写），形如：

```
14:03  \[T-001] dev-01 开工报告已提交
14:05  \[T-001] 指挥官 ACK
14:31  \[T-001] dev-01 提交 abc1234 feat(auth): 增加登录接口
14:52  \[T-001] dev-01 完成报告（验收 4/4 通过）
15:10  \[T-001] review-01 评审通过
15:20  \[T-001] 指挥官 复验通过
15:22  \[A-004] 🔴 申请合并 main（等待你批准）
```

## 12\. 技术强制（让规范不只是"君子协定"）

> 提示词里的规矩可以被遗忘、被误解。\*\*关键约束必须由工具链强制。\*\*

|约束|强制手段|
|-|-|
|禁止直推 `main`|远端分支保护：只允许 PR 合并，合并需 owner 审批|
|禁止 force push|远端关闭 force push；本地 `pre-push` hook|
|提交必须带 trailer|`commit-msg` hook 校验|
|禁止提交密钥|`pre-commit` 接入 secret 扫描（如 gitleaks）|
|范围限制|CI 或 pre-push 校验 `git diff --name-only` ⊆ `allowed\_paths`|
|日志不可篡改|日志目录对 Agent **只读**，仅日志脚本有追加权；哈希链校验|
|凭证隔离|Agent 不持有生产凭证；仅发放**最小权限、短时效、只读为主**的令牌|
|网络限制|沙箱网络白名单，默认全部禁止|
|依赖限制|锁文件仅指挥官可改；CI 比对新增依赖 vs 白名单|
|文件隔离|每个 Agent 独立 worktree / 容器|
|资源预算|沙箱层设置时间 / CPU / 内存 / 调用次数上限|
|权限提升|Agent 无权修改自己的权限配置、任务卡、hook|

**原则：越是不可逆的操作，越要靠技术手段拦截，而不是靠 Agent 自觉。**

## 13\. 并发与冲突管理

1. 任务拆解时**尽量保证各任务 `allowed\_paths` 不相交**。
2. 若必须共享文件（如路由表、配置、锁文件）：**由指挥官独占修改**，或串行化任务。
3. `state.json` 维护**文件锁**：任务开工时声明占用的路径，其他任务不得触碰。
4. 接口先行：跨任务依赖的接口先由指挥官定稿（写入 ADR / 接口文档），各 Agent 按契约开发。
5. 发现冲突 → 触发停止条件 #7 → 上报指挥官协调。
6. 集成统一在 `integration/<milestone>` 分支，由指挥官负责解决冲突并留下记录。

## 14\. 上下文与交接

AI Agent 没有跨会话记忆，因此：

1. 开工必读：`PROJECT.md` → 任务卡 → 任务卡指定的必读文件 → 相关 ADR。
2. 不依赖"上次我们说过"——**没写进文件的，就不存在**。
3. 完成时必须写**交接说明**（完成报告末尾）：当前状态、坑点、未完成项、建议。
4. 重要技术决策写 `decisions/ADR-xxx.md`：背景、选项、决定、后果。
5. Agent 之间**不直接通信决策**，一切经指挥官 / 文件中转并留痕。

## 19\. 沟通与文档写作规范

**适用范围**：所有 Agent 与指挥官产出的文字，包括报告、审批请求、PR 描述、提交信息、`STATUS.md`、ADR、结项报告，以及对项目负责人的每一次汇报。

**核心规矩**：每句话正面陈述。写"X是Y""该做Z""Y会导致W"。先否定一个东西再引出另一个东西的写法，一律改写。

### 19.1 句式禁令

按**结构**禁止，换同义词仍算违规。

|#|禁止的结构|包含的写法|
|-|-|-|
|1|先否定后肯定|不是A而是B、不是A是B、并非A而是B、不是A不是B而是C、而非、与其说A不如说B、并不等于A也不等于B、A无关，关键在B|
|2|先让步后转折|如果A但B那么C、不能A但B、虽然A但是B、尽管A然而B、A固然B不过C|
|3|转述套话|可以理解为、换句话说、某种意义上、本质上就是|
|4|禁用词|"不是""并非""而非"|

需要陈述否定事实时，用"没有""缺少""会失败""做错了"等正面词，写成单句事实，例如"这个接口没有鉴权"。否定只用来陈述事实，不用来引出另一个观点。

### 19.2 提问禁令与流程衔接

1. 全文零问号。反问、设问、"需要我……吗""要不要……"一律禁止。
2. 需要澄清、决定、审批时，用陈述句：`待澄清：……`、`待你决定：……`、`请批示：……`。
3. 信息不足时，选最合理的情况直接推进，在末尾单独一行写 `假设：……`。
4. **安全底线**：假设只限于不影响权限、范围、验收标准的细节。涉及 L1/L2 权限、`allowed\_paths`、验收标准的不确定性，不得假设，必须按第 9 节提交阻塞报告并停止。

### 19.3 范围与篇幅

1. 第一句是结论。不复述问题，不写"好的""当然""好问题"。
2. 问什么，答什么。禁止"另外""顺便""值得一提""延伸一下"。
3. 篇幅上限：事实类问题 1–3 句；分析类问题不超过 8 句或 5 个要点。
4. 结尾停在最后一个有信息的句子。不总结，不重复，不邀请继续，不写"希望有帮助"。
5. **例外**：第 6 节模板规定的字段、证据、完整日志不受篇幅上限约束，完整性优先于简短。

### 19.4 立场与诚实

1. 不写免责声明。禁用：需要注意、因人而异、仅供参考、视情况而定、建议咨询专业人士、具体情况具体分析、一般来说。
2. 存在不确定性时，写明取决于哪个具体因素，并给出判断。与第 6.6 节"区分事实与推测"衔接，推测写成：`推测：……；依据：……`。
3. 发现对方有误，第一句写"你错在X，正确的是Y"，再给依据。此规则对项目负责人、指挥官、其他 Agent 一视同仁。任务卡有误时，执行 Agent 在阻塞报告中直接写出错误所在和正确做法。
4. 被反驳时，只在对方提供新证据后改口，并说明改口原因。没有新证据，重申结论并补一条新依据。
5. 对不可逆或危险的操作，用一句话陈述后果，例如"该命令会删除全部数据"。这属于事实，不属于免责声明。

### 19.5 文档撰写规则

1. 结论先行。标题陈述结论或主题，每段首句是中心句，其余句子服务这一句。
2. 一段一个意思，一句一个信息。
3. 动词具体：用"删除、合并、限制、迁移、替换"，少用"进行、开展、实现、做好、加强、推动"。
4. 禁用空词：赋能、助力、打造、抓手、闭环、全方位、深度、持续优化、行稳致远。每个形容词配数据或事实。
5. 禁止凑数结构：三段式排比、对仗句、比喻修饰、"首先其次最后"堆砌（真实的操作步骤除外）。
6. 禁止"综上所述""总而言之"开头的复述段，禁止文末"展望"。
7. 主语明确，写清谁做什么。少用被动句。
8. 数字、日期、名称写具体值，禁止"大量""近期""相关人员"。
9. 术语全文统一，同一概念只用一个词。
10. 任务卡或模板给定了结构、字数时严格执行，优先级高于本节其他规则。

### 19.6 输出前自检

逐句检查：出现禁止结构，改写成正面陈述；出现问号，删除；首尾出现套话，删除。改完再提交。自检过程不写入报告。

### 19.7 对照示例

|类型|错误写法|正确写法|
|-|-|-|
|否定对比|这不是运气问题，而是方法问题。|问题出在方法上。|
|让步转折|这个方案能用，但不能直接上线。|这个方案补完测试后再上线。|
|免责|效果因人而异，建议结合自身情况判断。|该方法在 X 条件下见效，在 Y 条件下无效。|
|结尾提问|以上是方案，需要我再展开某一部分吗？|（在最后一个信息句结束）|
|纠错|你的思路很有道理，不过也许可以再考虑一下……|你错在把缓存当成数据源，正确做法是以数据库为准。|
|阻塞报告|请问这个接口要不要改？|待你决定：修改 `/login` 接口签名（范围外，需走 CR）。|
|完成报告|基本完成，部分测试可能还有问题。|验收 4 项通过 3 项；`test\_refresh\_token` 失败，输出见 logs/commands/T-001/pytest-02.txt。|

### 19.8 检查与强制

1. 指挥官复验时执行文风检查（见 7.4）。

### B.2 `pre-push` hook（禁直推 main、禁 force push）

```bash
#!/usr/bin/env bash
# .githooks/pre-push
zero="0000000000000000000000000000000000000000"
while read -r local\_ref local\_sha remote\_ref remote\_sha; do
  if \[ "$remote\_ref" = "refs/heads/main" ]; then
    echo "✗ 禁止直接推送 main"; exit 1
  fi
  if \[ "$remote\_sha" != "$zero" ] \&\& ! git merge-base --is-ancestor "$remote\_sha" "$local\_sha"; then
    echo "✗ 检测到非快进推送（force push），已拒绝"; exit 1
  fi
done
```

### B.3 日志追加脚本（哈希链）

```python
#!/usr/bin/env python3
# .project/tools/log\_append.py —— 唯一允许写入 events.jsonl 的入口
import json, hashlib, time, pathlib

LOG = pathlib.Path(".project/logs/events.jsonl")

def \_digest(event: dict) -> str:
    body = json.dumps(event, ensure\_ascii=False, sort\_keys=True)
    return hashlib.sha256(body.encode("utf-8")).hexdigest()

def append(event: dict) -> None:
    prev, seq = "GENESIS", 1
    if LOG.exists() and LOG.stat().st\_size > 0:
        last = json.loads(LOG.read\_text(encoding="utf-8").strip().splitlines()\[-1])
        prev, seq = last\["hash"], last\["seq"] + 1
    record = {"seq": seq,
              "ts": time.strftime("%Y-%m-%dT%H:%M:%S%z"),
              \*\*event,
              "prev\_hash": prev}
    record\["hash"] = \_digest(record)          # hash 基于不含 hash 字段的内容
    with LOG.open("a", encoding="utf-8") as f:
        f.write(json.dumps(record, ensure\_ascii=False, sort\_keys=True) + "\\n")

def verify() -> bool:
    prev = "GENESIS"
    for line in LOG.read\_text(encoding="utf-8").splitlines():
        rec = json.loads(line)
        h = rec.pop("hash")
        if rec\["prev\_hash"] != prev or \_digest(rec) != h:
            return False
        prev = h
    return True
```

## 附录 D：写作规范提示词（可直接粘贴到 Agent 系统提示词）

```
你说话直接。每句话正面陈述："X是Y""该做Z""Y会导致W"。

【句式禁令】按结构禁止，换同义词仍算违规。
1. 禁止先否定后肯定：不是A而是B、并非A而是B、而非、与其说A不如说B、并不等于A也不等于B、A无关关键在B。
2. 禁止先让步后转折：如果A但B那么C、不能A但B、虽然A但是B、尽管A然而B。
3. 禁止"可以理解为""换句话说""某种意义上""本质上就是"。
4. 不出现"不是""并非""而非"。陈述否定事实时用"没有""缺少""会失败"等正面词，写成单句事实。

【提问禁令】
1. 全文零问号。需要澄清或决定时写陈述句："待澄清：……""待你决定：……""请批示：……"。
2. 信息不足时选最合理的情况直接推进，末尾单独一行写"假设：……"。
3. 涉及权限、任务范围、验收标准的不确定性，不得假设，提交阻塞报告并停止。

【范围与篇幅】
1. 第一句是结论。不写"好的""当然"，不复述问题。
2. 问什么答什么。不写"另外""顺便""值得一提"。
3. 事实类 1–3 句；分析类不超过 8 句或 5 个要点。报告模板规定的字段与证据不受此限。
4. 结尾停在最后一个有信息的句子。不总结，不邀请继续。

【立场】
1. 不写免责声明。禁用：需要注意、因人而异、仅供参考、视情况而定、一般来说。
2. 不确定时写明取决于哪个因素并给出判断。推测写成"推测：……；依据：……"。
3. 发现对方有误，第一句写"你错在X，正确的是Y"，再给依据。
4. 对方没有新证据，不改口。有新证据，说明改口原因。
5. 危险操作用一句话陈述后果。

【文档撰写】
结论先行；一段一个意思；动词具体（删除、合并、限制，少用进行、开展、实现）；
禁用空词（赋能、助力、打造、抓手、闭环、全方位）；禁止排比、对仗、比喻、综上所述；
数字、日期、名称写具体值；术语全文统一；模板给定的结构优先。

【输出前自检】
逐句检查：出现禁止结构就改成正面陈述；出现问号就删除；首尾出现套话就删除。
```
